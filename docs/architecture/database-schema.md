## Data Storage Overview

### Current Implementation: localStorage

The application persists all task data in the browser's localStorage using JSON serialization. This approach was chosen for:

- **Zero backend dependency**: No server or database infrastructure required
- **Instant setup**: Works immediately without configuration
- **Offline support**: Data is always available locally
- **Privacy**: User data never leaves their device

### Storage Mechanism

```
User Action -> useKanban Hook -> useLocalStorage Hook -> JSON.stringify() -> localStorage
                                                                                    |
User Load   <- useKanban Hook <- useLocalStorage Hook <- JSON.parse()   <-----------+
```

### Hydration Handling

Since localStorage is not available during server-side rendering (SSR) in Next.js, the application implements hydration protection:

1. Initial render uses empty/default state
2. `useEffect` reads localStorage after mount
3. `isHydrated` flag indicates when client data is loaded
4. Components can show loading states until hydrated

## Entity Schemas

### Task Entity

The primary data entity representing a single task on the Kanban board.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `id` | `string` | Yes | Unique identifier (timestamp + random string) |
| `title` | `string` | Yes | Task title (max 100 characters) |
| `description` | `string` | Yes | Task description (max 500 characters) |
| `priority` | `Priority` | Yes | Task priority level |
| `tags` | `string[]` | Yes | Array of tag strings (max 10 tags, 30 chars each) |
| `columnId` | `ColumnId` | Yes | Current column/status of the task |
| `createdAt` | `string` | Yes | ISO 8601 timestamp of creation |
| `updatedAt` | `string` | Yes | ISO 8601 timestamp of last update |

#### TypeScript Definition

```typescript
interface Task {
  id: string;
  title: string;
  description: string;
  priority: Priority;
  tags: string[];
  columnId: ColumnId;
  createdAt: string;
  updatedAt: string;
}
```

#### Field Details

**`id`**
- Format: `{timestamp}-{random9chars}`
- Example: `1706284800000-k8f3j2m1n`
- Generated by `generateId()` utility function
- Guaranteed unique within reasonable probability

**`title`**
- User-provided task name
- Sanitized for XSS prevention (HTML entities escaped)
- Maximum length: 100 characters

**`description`**
- User-provided task details
- Sanitized for XSS prevention
- Maximum length: 500 characters
- Can be empty string

**`priority`**
- Enum value determining visual styling and importance
- Valid values: `'low'` | `'medium'` | `'high'`

**`tags`**
- Array of categorization labels
- Each tag sanitized for XSS
- Maximum 10 tags per task
- Maximum 30 characters per tag

**`columnId`**
- Determines which Kanban column displays the task
- Valid values: `'todo'` | `'in-progress'` | `'completed'`

**`createdAt` / `updatedAt`**
- ISO 8601 format timestamps
- Example: `2026-01-26T10:30:00.000Z`
- `updatedAt` changes on any modification or move operation

### Column Entity

Represents a Kanban board column. Currently defined as constants rather than stored data.

| Field | Type | Description |
|-------|------|-------------|
| `id` | `ColumnId` | Unique column identifier |
| `title` | `string` | Display name for the column |

#### TypeScript Definition

```typescript
type ColumnId = 'todo' | 'in-progress' | 'completed';

interface Column {
  id: ColumnId;
  title: string;
}
```

#### Predefined Columns

```typescript
const COLUMNS: Column[] = [
  { id: 'todo', title: 'To-Do' },
  { id: 'in-progress', title: 'In Progress' },
  { id: 'completed', title: 'Completed' },
];
```

### Priority Type

Enumeration for task priority levels.

```typescript
type Priority = 'low' | 'medium' | 'high';
```

| Value | Display | Color Scheme |
|-------|---------|--------------|
| `low` | Low | Emerald/Green |
| `medium` | Medium | Amber/Orange |
| `high` | High | Rose/Red |

## Data Relationships

### Entity Relationship Diagram

```
+----------------+       references       +----------------+
|     Task       |----------------------->|     Column     |
+----------------+                        +----------------+
| id: string     |                        | id: ColumnId   |
| title: string  |                        | title: string  |
| description    |                        +----------------+
| priority       |                              ^
| tags: string[] |                              |
| columnId ------+----- FK to Column.id --------+
| createdAt      |
| updatedAt      |
+----------------+
```

### Relationship Details

- **Task to Column**: Many-to-One
  - Each task belongs to exactly one column
  - Each column can contain zero or more tasks
  - Relationship enforced by `columnId` field
  - Column definitions are static (not user-modifiable)

- **Task to Tags**: One-to-Many (embedded)
  - Tags are stored as an array within the task
  - No separate tag entity exists
  - Duplicate tags across tasks are independent strings

## Data Migration Considerations

### Current State

The application does not currently implement formal data migrations. Schema changes require manual handling.

### Recommended Migration Strategy

For future schema changes, implement a versioning system:

```typescript
interface StorageSchema {
  version: number;
  tasks: Task[];
}

const CURRENT_VERSION = 1;

function migrateData(stored: unknown): Task[] {
  // Handle legacy format (array without version)
  if (Array.isArray(stored)) {
    return migrateV0ToV1(stored);
  }

  const schema = stored as StorageSchema;

  switch (schema.version) {
    case 1:
      return schema.tasks;
    // Add future migrations here
    default:
      return schema.tasks;
  }
}
```

### Migration Best Practices

1. **Never delete data without backup**: Store old format temporarily
2. **Version your schema**: Track changes with version numbers
3. **Make migrations idempotent**: Safe to run multiple times
4. **Test with real data**: Use production-like datasets
5. **Provide rollback path**: Allow reverting if issues arise

### Example Migration: Adding a New Field

```typescript
// Migration: Adding 'dueDate' field to tasks
function migrateV1ToV2(tasks: TaskV1[]): TaskV2[] {
  return tasks.map(task => ({
    ...task,
    dueDate: null, // New field with default value
  }));
}
```

## localStorage Limitations

### Size Constraints

| Browser | Storage Limit |
|---------|---------------|
| Chrome | 5-10 MB |
| Firefox | 5 MB |
| Safari | 5 MB |
| Edge | 5-10 MB |

### Practical Capacity

Assuming average task size of ~500 bytes (JSON serialized):

| Task Count | Approximate Size |
|------------|------------------|
| 100 tasks | ~50 KB |
| 1,000 tasks | ~500 KB |
| 5,000 tasks | ~2.5 MB |
| 10,000 tasks | ~5 MB (limit) |

### Other Limitations

| Limitation | Impact |
|------------|--------|
| **Synchronous API** | Blocks main thread during read/write |
| **String-only storage** | Requires JSON serialization overhead |
| **No querying** | Must load all data to filter/search |
| **Single-device** | No cross-device synchronization |
| **No concurrent access** | Multiple tabs can cause conflicts |
| **User clearable** | Users can delete via browser settings |
| **Private browsing** | May not persist in incognito mode |

### Handling Storage Errors

```typescript
try {
  localStorage.setItem(key, JSON.stringify(data));
} catch (error) {
  if (error instanceof DOMException) {
    if (error.name === 'QuotaExceededError') {
      // Storage is full
      console.error('localStorage quota exceeded');
    } else if (error.name === 'SecurityError') {
      // localStorage blocked (e.g., private browsing)
      console.error('localStorage access denied');
    }
  }
}
```

## Future Database Considerations

If the application needs to scale beyond localStorage limitations, consider these alternatives:

### Option 1: IndexedDB (Client-Side)

**Pros:**
- Larger storage capacity (>50MB typical)
- Asynchronous API
- Supports indexes for querying
- Still fully client-side

**Cons:**
- More complex API
- Still single-device
- No built-in sync

**Migration Path:**
```typescript
// IndexedDB schema equivalent
const db = await openDB('kanban', 1, {
  upgrade(db) {
    const store = db.createObjectStore('tasks', { keyPath: 'id' });
    store.createIndex('columnId', 'columnId');
    store.createIndex('priority', 'priority');
    store.createIndex('updatedAt', 'updatedAt');
  },
});
```

### Option 2: SQLite (via sql.js or wa-sqlite)

**Pros:**
- Full SQL query capabilities
- Familiar relational model
- Can export/import easily

**Cons:**
- Larger bundle size
- Still client-side only

**Schema:**
```sql
CREATE TABLE tasks (
  id TEXT PRIMARY KEY,
  title TEXT NOT NULL,
  description TEXT,
  priority TEXT CHECK(priority IN ('low', 'medium', 'high')),
  column_id TEXT CHECK(column_id IN ('todo', 'in-progress', 'completed')),
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE task_tags (
  task_id TEXT REFERENCES tasks(id) ON DELETE CASCADE,
  tag TEXT NOT NULL,
  PRIMARY KEY (task_id, tag)
);

CREATE INDEX idx_tasks_column ON tasks(column_id);
CREATE INDEX idx_tasks_priority ON tasks(priority);
```

### Option 3: Backend Database (Full Stack)

**PostgreSQL Schema:**
```sql
CREATE TABLE users (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  email TEXT UNIQUE NOT NULL,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE boards (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID REFERENCES users(id) ON DELETE CASCADE,
  name TEXT NOT NULL,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE columns (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  board_id UUID REFERENCES boards(id) ON DELETE CASCADE,
  title TEXT NOT NULL,
  position INTEGER NOT NULL,
  UNIQUE(board_id, position)
);

CREATE TABLE tasks (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  column_id UUID REFERENCES columns(id) ON DELETE CASCADE,
  title TEXT NOT NULL,
  description TEXT,
  priority TEXT CHECK(priority IN ('low', 'medium', 'high')),
  position INTEGER NOT NULL,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE tags (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name TEXT UNIQUE NOT NULL
);

CREATE TABLE task_tags (
  task_id UUID REFERENCES tasks(id) ON DELETE CASCADE,
  tag_id UUID REFERENCES tags(id) ON DELETE CASCADE,
  PRIMARY KEY (task_id, tag_id)
);
```

**Benefits of Backend Database:**
- Multi-device synchronization
- User authentication
- Collaboration features
- Unlimited storage
- Advanced querying
- Data backup and recovery

### Migration Checklist

When migrating from localStorage to a database:

- [ ] Export existing localStorage data
- [ ] Design new schema with proper normalization
- [ ] Create data transformation scripts
- [ ] Implement API endpoints for CRUD operations
- [ ] Update hooks to use API instead of localStorage
- [ ] Add authentication layer
- [ ] Implement optimistic updates for UX
- [ ] Add offline support with sync queue
- [ ] Test data integrity after migration
- [ ] Provide fallback for failed migrations
